PRD Builder · 项目模式交付示例

两页 · 两会话并行 需求：意见反馈
虚构示例：本页所有字段、状态、规则、数字均为演示格式而造，不是真实需求，也不构成任何业务规则。 真实项目里每个页面目录只放自己的产物。

一份需求，四种产物

产品需求文档

PRD.md

唯一权威文本。目标与范围 → 场景与流程 → 功能与规则（R 编号）→ 验收标准（G 编号）→ 影响与开放问题。规则只写一遍，验收只验证规则。

机器可读规格

spec.yaml

把同一份需求压成结构和编号：scope / roles / refs / rules / acceptance / tasks / open_questions。研发 Agent 直接读它拆任务，不再从自然语言里猜。

可交互原型

mocks/*.html

单文件内联，无外链字体与框架，离线可打开。布局与交互用文字说不清时才画，纯规则、纯接口不画。

评审版

review.html

脚本把 PRD 正文、规格摘要、内嵌原型拼成一张人读页面，带目录与交叉引用锚点。不能手写，改完产物重跑脚本生成。

spec.yaml 长这样（节选）

rules:
  - { id: R-02-002, text: 一条反馈同一时间只能被一名运营领取，
      已被他人领取时领取按钮置灰并显示领取人 }

acceptance:
  - { id: G-02-001, given: 存在 1 条待处理反馈,
      when: 运营 A 点领取, then: 状态变为处理中，领取人显示运营 A }

tasks:
  - { id: T-02-002, title: 后台反馈处理页, depends_on: [T-02-001],
      done_when: G-02-001 与 G-02-002 验收通过 }

open_questions:
  - { id: Q-02-01, question: 回复后是否需要通知用户, owner: 产品 }

两个页面，各有自己的产物

01
提交反馈
用户端表单。主管「反馈」实体与状态机，02 页通过 refs 引用，不重复定义。
查看评审版 →
02
反馈处理
运营后台列表、领取、回复与退回。引用 01 的状态机，写清并发领取与部分失败。
